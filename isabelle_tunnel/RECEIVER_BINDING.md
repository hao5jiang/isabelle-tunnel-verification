## 本轮解决的问题

上一轮验证完整报文格式，但一份格式正确的报文仍可能被送到错误的接收位置。本轮增加独立的接收上下文，先检查报文应该交给谁，再决定能否调用协议事件。

本轮目标是**网络接收目标隔离**，不是设备本地动作的全面权限隔离，也不是身份认证。

## 接收规则

| 报文类型 | 设备字段含义 | 可接受的接收位置 |
|---|---|---|
| 进入命令，类型 1 | 命令目标 A 或 B | 对应的 DevicePort A 或 DevicePort B |
| 轮次隔离请求，类型 2 | 命令目标 A 或 B | 对应的 DevicePort A 或 DevicePort B |
| 清场确认，类型 3 | 声称发送确认的设备 A 或 B | ControllerPort |

确认报文中的设备字段不是接收目标。因此控制器能够接收 A、B 两种确认，设备通道则不能接收确认。

`receiver_decode n L r bs` 先调用已经验证的 `frame_decode`。成功得到消息 p 后，还要求 `packet_destination p = r`，才能返回成功。

r 是**可信本地接收上下文**，不从报文头读取。实际部署时，服务程序必须将 socket 或设备入口与该上下文可靠绑定。测试程序中的逻辑编号 0、1、2 分别表示控制器、设备 A、设备 B，不是 TCP／UDP 端口号。

报文格式没有改变：仍是六字节首部加 n 字节小端轮次。原有格式、范围和完整长度检查继续生效。

## 形式证明内容

| 定理 | 结论 |
|---|---|
| `receiver_decode_exact` | 成功当且仅当原报文解析成功且目标与接收上下文一致 |
| `receiver_decode_roundtrip` | 合法消息编码后交给正确接收端，恢复原消息 |
| `receiver_decode_unique_port` | 同一配置下，同一报文不能在两个不同接收通道成功解析 |
| `device_port_actions` | 设备 i 的网络入口只能产生给 i 的进入或隔离事件 |
| `controller_port_actions` | 控制器网络入口只能产生接收确认事件 |
| `receiver_network_cannot_generate_ack` | 网络输入不能调用本地确认生成动作 |
| `receiver_wrong_port_stutters` | 格式正确但接收端错误的输入，不改变协议状态 |
| `receiver_correct_port_matches_datagram` | 正确接收端的效果与上一轮数据报层一致 |
| `receiver_run_refines_finite` | 过滤拒绝项、解出事件后，新层与有限轮次协议得到同一最终状态 |
| `receiver_mutual_exclusion` | 在既有模型假设下，对于每条事件序列，两列车不会同时占用隧道 |
| `receiver_exhaustion_persists` | 最后轮次停发条件在后续执行中保持 |

本地操作仍是独立的 `ReceiverLocal` 接口，不受接收通道筛选。`receiver_local_exact` 证明它与原有限协议动作完全一致；`receiver_local_ignores_frame_configuration` 证明改变报文字段宽度不会阻止该接口。轮次上限 L 仍参与原协议规则，不因此被忽略。

## 错误入口的见证

`ignoring_receiver_port_can_actuate_other_device` 使用原有可达状态：A 的最后合法轮次命令已经发出，控制器已停发，两车目前都在隧道外。

把 A 的有效命令送到 B 接收通道：

- 新入口拒绝，整个模型状态不变。
- 忽略接收上下文、直接使用旧数据报入口，会调用 A 的进入事件，使 A 在模型中进入。

这证明目标绑定策略能够区分错误入口。它没有证明现实中的 B 会执行 A 的命令，也没有声称该差异单独导致两车碰撞。

## 实际导出与运行入口

`Receiver_Codegen.thy` 将目标检查与解码直接导出为 `generated/ReceiverGate.ML`，同时保留报文编码函数用于测试。没有导出整个控制器、日志系统或物理执行器。

`generated_receiver_cli.ML` 只有以下文本命令：

| 命令 | 示例 | 结果 |
|---|---|---|
| 入口探针 | `V` | `ISABELLE_RECEIVER_GATE_V1` |
| 编码 | `E 2 65535 1 0 513` | `B 84 75 1 1 0 2 1 2` |
| 在设备 A 上接收 | `R 2 65535 1 84 75 1 1 0 2 1 2` | `P 1 0 513` |
| 同一报文交给设备 B | `R 2 65535 2 84 75 1 1 0 2 1 2` | `N` |
| 同一报文交给控制器 | `R 2 65535 0 84 75 1 1 0 2 1 2` | `N` |

没有未绑定的 `D` 解码命令。`R` 中的接收编号由本地调用者提供；这份文本测试入口不是对不可信远程调用者的权限认证服务。如果远程输入能控制这个参数，真实部署的绑定前提就不成立。

核心拒绝返回 `N`，文本或运行策略拒绝返回 `X`。负号等非法文本在转换为自然数前拒绝。每条回复刷新输出，超长输入按既有策略拒绝后，后续行仍可处理。

形式格式允许 n=1–255；文本入口仅开放 n=1–64，单个数字串最多 160 字符、每行最多 132 个字段与 16,384 字符。`R` 有四个前置字段，因此最多 128 个字节项进入解析核心；超出该接口限制返回 `X`。这些运行限制没有构成资源安全的形式证明。

## 执行检查的方法

`check_generated_receiver.py` 明确把核心绝对路径交给运行器，真实启动 Poly/ML。预期报文字段由 Python 标准字节转换计算，接收角色由独立的六项对应表判断，不用被测入口的目标分支当作预期结果。

实际请求覆盖：

- 六种类型／设备组合分别进入三个通道，明确检查每种接受和拒绝。
- 一字节上限 0、1、127、255 与每个轮次的编码及三个通道接收。
- 完整双字节轮次域上的进入命令和确认，分别交给正确与错误通道。
- 首部变异、超范围轮次、无效逻辑接收编号、畸形文本、旧的未绑定命令、入口资源限制与出错后恢复。
- 两次输入仍保持开启时的交互回复，以及批量最后一行没有换行的 EOF 处理。

测试要求退出码为 0、标准错误为空、结果内容和条数完全匹配，并检查核心、入口、运行器的前后哈希。五个故意错误回复用于检查答案比较器。约 1.35 秒的本次批量执行时间不是性能保证。

独立协议模型另检查了 268,288 份报文在三个通道的结果，13,524 次协议转换检查、60 次轨迹中的错误通道状态不变、248 个崩溃插入位置、深度 2 搜索的 392 个状态／8,426 条转移，以及固定种子测试。有效报文在三个合法通道中恰好有一个可接受位置；这不代表发送者已认证。

### 错误副本是否真的被发现

`check_receiver_negative_controls.py` 只创建隔离副本，不修改正式导出。

1. 将目标判断改为始终通过。副本仍能编译，但实际测试发现控制器接收 A 的进入命令时，本应返回 `N`，却返回 `P 1 0 42`。这项检查要求明确的结果差异，不能用编译失败充数。
2. 加入语法错误。实际启动失败，编译诊断指向指定副本，不回退加载正式核心。
3. 只加注释。16,620 条较小测试集和两条交互检查通过，但文件 SHA256 与正式导出不同，说明行为测试不能替代来源核对。

结束后确认正式核心未变。这些控制检验本次注入的错误，不是对测试框架完备性的证明。

## 可信边界

本轮继续依赖可信的命令／确认历史、真实占用观察、持久化与门槛规则，以及模型中的原子动作。`packet_train` 是报文标签，不是对发送者身份的证明。正确目标检查不替代来源认证、完整性保护或实际 socket 绑定。

拒绝输入在模型中不改变协议状态；日志写入、计数与限流没有建模。理论中的有限轮次不等于整个历史或存储空间有界；停发不取消在途命令，也不保证急停或清场。

生成程序的执行检查，不等于形式验证了文本入口、编译器、操作系统、网络、固件或机器码。
