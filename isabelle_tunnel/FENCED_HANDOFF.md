本轮把上一轮理想化的“确认清场”条件展开成消息协议。控制器提交时不直接读取远端占用或网络中的命令，而是检查两台设备发来的新轮次确认。证明再从这些确认的来源规则，推出设备确已退出、旧命令已不能执行。

这仍是抽象协议验证，不是实际硬件、网络认证或文件系统实现的验证。

## 协议如何工作

持久记录保存 `(轮次, 许可持有者)`。许可持有者可以是 A、B，或没有持有者。

1. 控制器停止发出进入命令，准备下一轮的持久记录，并向两台设备发送隔离请求。
2. 设备收到请求后提高本地拒绝门槛：低于该轮次的进入命令不能执行。提高门槛不会让已经进入的设备凭空退出。
3. 设备确实已退出、且门槛已提高后，才发出该轮次的清场确认。
4. 控制器分别收到两台设备的确认，并完成日志写入后，才能提交新轮次许可。
5. 新许可提交成功后，控制器恢复命令发放。设备执行进入动作时仍检查本地轮次门槛。

数据写入、消息到达、设备退出与确认接收是分开的事件，可以交错。规则并不要求网络删除旧报文；已发送报文的历史保留下来，允许延迟、重复到达，或持续不被投递。

### 为什么确认不会马上过期

设当前已提交轮次是 g。新确认对应 g+1。设备发出确认时已经退出，并把门槛提高到至少 g+1；此前已发出的进入命令轮次不超过 g。因此，从发出确认到新许可提交之间，这些旧命令不能使设备重新进入。

这是证明中的核心不变量，不是“收到确认就假定永远为空”。提交后可以发新轮次命令；之后的交接必须再次使用更高轮次的确认。

## 崩溃行为

控制器崩溃会取消未完成的日志事务、清空本地已收到的确认，并停止发命令，但不清除设备占用、设备拒绝门槛或网络报文历史。

如果在提交前崩溃，恢复的仍是旧许可；设备已经提高的门槛继续阻止旧命令。控制器需要重新准备并写入交接记录，不能只靠重复 Commit 启用残留数据。

未提交轮次的真实旧确认可以再次投递：该轮次尚未用于发命令，设备门槛也没有降低，所以这些确认仍可安全使用。如果该轮次已经提交，下一次交接需要更高轮次，旧确认不能代替它。

没有承诺持续崩溃或持续不投递消息时仍能完成服务；这些情况下协议可以安全停住。

## 形式定理对应

| 定理 | 结论 |
|---|---|
| `fence_step_valid`、`fence_history_valid` | 对于每个合法事件及每条执行的有限前缀，协议不变量保持 |
| `fenced_all_interleavings_safe` | 两台设备不会同时实际占用区域，不需要公平性假设 |
| `acknowledgements_establish_quiescence` | 新轮次确认齐备时，实际占用为空、仍能执行的进入命令也为空 |
| `old_epoch_entry_rejected` | 比当前已提交轮次更旧的进入报文被拒绝 |
| `acknowledged_fence_rejects_older_entry` | 已确认的设备门槛会拒绝更低轮次的进入报文 |
| `crash_keeps_fences_and_commands`、`crash_stops_emission` | 控制器崩溃保留设备隔离状态和旧命令，并停止新命令发放 |
| `projection_satisfies_admission_invariant` | 新协议的状态投影满足上一轮的许可覆盖不变量 |
| `received_handshake_meets_admission_guard` | 收到的确认足以建立上一轮要求的清场条件 |
| `delayed_old_command_survives_but_cannot_enter` | 具体交接与重启流程中，A 的旧命令仍存在，但最后只有 B 在区域内 |
| `resetting_endpoint_floor_can_collide` | 错误地清空设备轮次门槛后，旧命令可以导致双占用 |

最后两项提供了正常完成见证和错误实现反例，避免只有“始终不发命令”的安全结论。

## 与上一轮的关系

`fence_projection` 保留双槽日志结构，只去掉载荷中的轮次字段；将仍能通过设备门槛的命令映射为 `issued`，将设备实际占用映射为 `occupants`。

已证明该投影满足 `Durable_Admission` 的状态不变量，并且消息确认能建立其交接条件。并未证明每一步都对应旧模型中的一个动作：提高门槛会使旧命令失效，而旧模型没有对应的“取消命令”事件。因此本轮称为状态不变量与交接条件的连接证明，不称为完整逐步精化。

没有自动继承前面编号控制器的请求计数、最终服务或有限编号性质；把这些层接成同一套系统仍需要独立证明。

## 仍需要实现与验证的条件

1. **设备端轮次门槛不能丢失或回退。** 本模型包含控制器崩溃，不包含会清空门槛的设备重启。反例已经说明这项条件不能省略。下一步应验证设备侧门槛的持久化、重启和失效处理。
2. **执行动作时必须检查轮次。** 仅在收到网络报文时检查，随后让过期的内部排队动作继续执行，并不满足本模型。实际设备需要本地执行门控或等价的取消、排空协议。
3. **确认必须来自真实设备，且占用读取真实。** `ack_history` 表示可信发送来源，不是已经实现密码认证。实际网络认证、错误传感器和恶意报文尚未验证。
4. **存储假设没有改变。** 日志完整写入、提交选择器原子且持久、崩溃不损坏完整记录，仍来自上一轮的抽象存储契约。
5. **自然数轮次不会回绕。** 还没有把已有的有限编号耗尽锁定接入这套消息协议。
6. **不保证每条执行都最终服务。** 没有实时上限、公平投递定理、实际制动距离或完整请求队列持久化证明。

建议下一步先处理设备端持久化与重启，再接入有限编号耗尽策略；这两项直接关系到旧命令是否会重新获得执行资格。
