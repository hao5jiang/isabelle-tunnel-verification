# 持久许可与设备动作：联动验证

日期：2026-10-02。

## 本轮范围

新增 `Durable_Admission.thy`，将双槽检查点与“发出进入命令、设备实际进入、设备实际退出、控制器崩溃”接在同一套状态转移规则中。

## 核心规则

| 部分 | 含义与约束 |
|---|---|
| `durable` | 双槽日志；恢复读取已提交记录，而非准备中的记录 |
| `issued` | 已发出但尚未执行的进入命令；不因控制器崩溃而清空 |
| `occupants` | 设备实际占用；不随检查点恢复而重写 |
| `EmitEnter` | 只有已提交记录许可该设备，才可发出进入命令 |
| `CommitReservation` | 更换许可持有者时，必须同时没有实际占用、没有待执行进入命令 |

准备和写入新记录期间，旧命令仍能执行，设备也仍能退出。提交时重新检查交接条件，不把“准备时区域为空”当成之后一直为空。

同一持有者的记录允许再次提交；改变持有者或清除许可，则需要清场条件。崩溃取消尚未完成的日志事务，但保留已提交许可、在途命令和设备占用。因此，重启后仍可安全完成崩溃前的进入动作。

## 定理对应

- `admission_step_valid`：对于每个合法事件，持久许可继续覆盖待执行命令和设备占用。
- `admission_history_valid`、`all_interleavings_safe`：从初始状态开始，对于每条事件序列的每个有限前缀，两台设备不会同时占用区域。事件序列可以包含多次崩溃，不需要公平性假设。
- `emit_requires_committed_owner`：未提交的许可不能用于发出进入命令。
- `crash_preserves_inflight_and_physical_state`：崩溃不会抹掉在途命令或实际占用。
- `inflight_entry_survives_crash`：崩溃前发出的进入命令，在崩溃后仍可执行；这里没有通过冻结设备来回避问题。
- `busy_handoff_blocked`：有占用或在途命令时，不能切换到不同的许可记录。
- `quiescent_handoff_commits`：清场条件成立，且新记录已完整写入、事务仍有效时，可以提交。
- `recovery_handoff_safe_and_completes`：具体恢复流程先允许 A 的在途命令完成，拒绝过早交接，待 A 退出后交给 B；最终只有 B 在区域中。

最后一项是具体有限流程的完成见证，不是无条件最终服务定理。持续崩溃、不执行命令、不退出或不断重复发命令，都可能阻止后续服务。

## 两个错误方案的反例

### 1. 先发命令、后提交

准备 A 的许可，完成数据写入，但没有提交；错误地先发 A 的进入命令，随后崩溃。恢复仍正确地读到旧的“没有许可”，但 A 的命令继续执行，设备进入。

`premature_emission_breaks_coverage` 表明：日志内部依旧有效，却已不能覆盖设备占用。这个错误发命令动作被明确放在正常协议之外，不是正常规则自身的反例。

### 2. 只检查区域为空，忽略在途命令

A 的许可已提交，进入命令已发出但还没执行。此时区域确实为空。错误地据此提交 B 的许可，再发 B 的命令。之后 A、B 的进入命令先后执行，形成双占用。

`ignoring_queued_command_can_collide` 给出了这条路径。它说明真实实现必须处理命令清空或隔离，单靠占用传感器不足以保证安全。

## 独立测试

`check_admission.py` 使用两种实现交叉检查：一份操作双槽日志，另一份只保存事务状态，不使用槽位或选择器。

- 遍历 180 个可达状态、2,160 条事件转移，安全条件与参考事务模型一致。
- 进行 100,000 次固定种子的混合事件测试。
- 检查一条服务与交接流程的 14 个崩溃插入位置。
- 检查崩溃后的延迟进入、安全交接及上述两个错误方案。
- 原有六组测试继续通过。

有限遍历仅合并不会被运行规则读取的历史记录前缀；实际槽位、选择器、事务状态、在途命令及设备占用仍参与状态区分。Python 是独立测试实现，不是 Isabelle 认证生成的程序；其遍历结果不能替代形式证明。

## 保留的实现义务

1. 存储仍采用前一层的假设：完整写入可持久化、提交选择器原子且持久、崩溃不破坏已完整记录。未验证 Windows 文件系统或实际磁盘。
2. “区域已空且没有在途命令”是理想的真实状态检查，并与提交按单步交错建模。不是证明控制器能凭一个普通网络应答就准确得知该事实。实际实现需要关闭旧许可的发命令入口、隔离旧命令并确认清场；应答返回到提交之间的竞态仍需要协议精化证明。
3. 命令按设备合并为集合项。没有建模多份重复报文、设备掉电后的记忆丢失、错误传感器、恶意命令或密码认证。
4. 没有证明与 `Numbered_Controller`、`Bounded_Identifiers` 的整体精化，也没有持久化请求计数或证明跨崩溃服务次数准确。
5. 没有实际运行时延、制动距离、可部署代码或实际硬件验收结论。

下一步最有价值的是将第二项改成显式的“停止旧命令发放 → 设备隔离旧轮次 → 清场确认 → 持久提交新许可”消息协议，并证明它实现本轮的交接条件。之后再接入已有轮次、会话和有限编号层。
